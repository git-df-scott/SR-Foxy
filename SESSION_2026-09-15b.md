that exists, and it is not one.

## 2. The non-ribbon side is closed, and this session did not reopen it

`research/02` §0 already answers the crux question: there is **no** known
computable invariant `I` with a theorem "K ribbon ⇒ I(K) = 0" that is not also
known to vanish at the handle-ribbon level. Every 2026 paper checked above
lands at `≤_h`, which `K_G` satisfies. Nothing found this session changes that
table. A non-ribbon proof for `K_G` still needs the universally quantified
statement of `research/06` — no derivative on any Seifert surface is an unlink
— which is Generalized Property R for an explicit 5-component R-link.

## 3. What was built: the search stack no longer needs Sage

The Dunfield–Gong band search is gated behind
`spherogram.links.bands.search.could_be_strongly_slice`, which needs SnapPy
inside Sage for `Link.signature()` and `exterior().fox_milnor_test()`. Two
sessions in this repository have lost time to that dependency, and this
container could not install `passagemath-standard` at all (repeated read
timeouts from `files.pythonhosted.org`).

`scripts/sagefree_slice_filter.py` replaces it with pure Python + numpy +
sympy:

* all pairwise linking numbers vanish;
* `signature(V + Vᵀ) = 0`, computed exactly over `Q` by congruence
  diagonalisation (Sylvester), `V` from `Link.seifert_matrix()`, which needs no
  Sage;
* `|det(V + Vᵀ)|` a perfect square, free from the same matrix;
* Fox–Milnor on `det(V − tVᵀ)` for one-component links, with a degree cap
  above which the link is kept;
* for multi-component links, the same three tests applied to **each
  component** — every component of a strongly slice link bounds a disk, so each
  is a slice knot. Spherogram's own filter does not do this.

Every test is a necessary condition for strong sliceness, and every failure
path returns `True`. So the replacement can only keep **more** links in the
search than the Sage version, never fewer: negatives remain valid coverage of
their box, and **no ribbon disk can be lost**. Same failure direction as the
existing `_safe_filter` patch in `scripts/teichner_certify.py`.

Signature checked against the tables on `3_1, 4_1, 5_1, 6_1, 6_2, 8_8, 9_46,
10_3, L2a1` — all match.

**Calibration [RESULT].** The filter rediscovers the repository's own
calibration target: the verified ribbon disk of `K_B` (31 crossings, the
0-friend of `K_G`) is found and `verify_ribbon_to_unknot`-verified in **1.3 s**,
against 0.9 s for the Sage stack in `results/KB_calibration_shaken20_bands2.json`.
Controls `6_1, 8_8, 9_46, 10_3` all found and verified; `6_3`, which is not
slice, correctly not found.

## 4. A measurement that changes how the Teichner lane should be run [RESULT]

`results/session_2026-09-15b/KB_band_length_floor.json`.

The `K_B` ribbon disk is found and verified at **`max_band_len = 2`**, in 1.2 s
— the same disk the repository found at length 8, and the same one the
saturation study reached at length 6.

Combined with `results/band_generator_saturation.json` (`max_band_len`
saturates at 6), this says something specific about where the lane's budget
has been going. The search stops early when it reaches an unlink, so a diagram
that *carries* a short ribbon disk is cheap; a diagram that does not carry one
costs the full frontier of its box. Every hour the Teichner lane has spent at
length 5 on one diagram bought frontier, not search: `D_{0,1} # 6_1` at
2 bands, length 5 took 4.21 h, and a disk of the kind that exists on `K_B`
would have shown up in the first seconds of a length-2 run.

**So the dial that matters for *finding* a disk is diagram count, not band
length.** Every Teichner run in this repository has used exactly one diagram.
That is the gap this session's runs attack.

## 7. A test that failed calibration and was withdrawn [NEGATIVE RESULT]

To speed the multi-component half of the filter I added two link-level tests:
`|det(L)|/2` a perfect square, and a Torres-corrected Fox–Milnor — divide
`det(V − tVᵀ)` by one factor of `t − 1`, then apply the knot test, on the
grounds that a slice link's multivariable polynomial is `f·f̄` (Kawauchi) and
`Δ_L(t) ≐ (t−1)·Δ_L(t,…,t)` (Torres).

**They failed calibration.** With them installed the search no longer finds the
known, verified ribbon disk of `K_B`: the run stopped terminating early, which
is the signature of a filter rejecting links that lie on a *genuine ribbon
movie*. Something in the chain is wrong — the Torres normalisation, the
Seifert-matrix convention, or the specialisation — and the failure direction is
the fatal one. A filter that can lose a disk can lose a counterexample.

Both are left in `scripts/sagefree_slice_filter.py`, unused, behind a comment
saying they must not be reinstated without re-running
`scripts/kb_band_length_floor.py`. Recording this because it is exactly the
error the campaign's standing cautions exist to catch, and it was caught by the
repository's own calibration discipline rather than by inspection.

## 8. The `L_{3,1}` lane, revived with the figure in hand

`research/22` §3.4 calls building `L_{3,1}` "the highest-value construction on
the board that is not another band search: the only place in the catalog where
a computable ribbon-only obstruction meets an open question." The blocker was
that GST Figure 1 is a picture.

**The picture is now in hand.** arXiv's source package for
[1103.1601](https://arxiv.org/abs/1103.1601) ships the figures as vector PDFs:
`Ln1.pdf` is Figure 1, `sliceknot.pdf` is Figure 2, `Lnk.pdf` is Figure 14, and
`Text.tex` carries the pin labels — the twist boxes are `−1` (left) and `+1`
(right), the spirals are `n strands`. Rendered copies are reproducible with
`pymupdf`.

Two things were verified from the primary source this session:

* **`L_{n,k}` is smoothly slice in the standard `B⁴`**, not merely in a
  homotopy ball. §8: "Since the pictured 4-manifold is actually diffeomorphic
  to a 4-ball [Go1], it follows that `L_{n,k}` is smoothly slice." So the
  Eisermann test has a genuinely slice target.
* **Its ribbon status is open exactly for the cases we want.** §8: "The authors
  do not know whether `L_{n,k}` is ribbon except in the special cases `n = 0,1`
  or `k = 0` or `(n,k) = (2,1)`."

Eisermann's determinant theorem was re-read at
[0802.2287](https://arxiv.org/abs/0802.2287) and is a congruence mod 32, as
`research/02` records — not an equality. The pre-registered test stands
unchanged: **if `L_{3,1}` is ribbon then `det V(L_{3,1}) ≡ 81 ≡ 17 (mod 32)`.**

Transcribing the figure by eye is still the wrong way in, because a
mis-read diagram gives a wrong Jones polynomial and could masquerade as a
violation. So this session instead **ran the repository's own
`scripts/gst_L31_shaken_fission.py`, which had never been run**: it recovers
`L_{3,1}` as a one-band fission of Regina's 48-crossing Figure 2 knot and
accepts only on component genus and fiberedness. Two workers are running, seeds
20260916 (80 diagrams, twists 2, length 7) and 777 (80 diagrams, twists 3,
length 6), against the single-diagram pass whose three candidates were all
rejected.

Diao–Pan–Yan (arXiv:2604.17737) were re-checked as a shortcut and ruled out:
their source package has no PD codes, braid words, isometry signatures or
ancillary data, and the paper states the construction algorithm "will be the
content of another paper".

## 9. Leads opened and cut this session

* **Cut — Agol–Ren finiteness as a non-ribbon route.** Their order is `≤_h`,
  and `K_G` is already handle-ribbon. Same for Dunkerley's ribbon-minimality.
* **Cut — Diao–Pan–Yan as a source of explicit R-links.** No published data.
* **Cut — fibered mutant pairs as Miyazaki targets.** `CANDIDATE_LEDGER.md`
  already records that mutation implies neither concordance nor its failure,
  and the Conway/Kinoshita–Terasaka pair shows mutants need not be concordant,
  so the family supplies candidates with no evidence, not candidates.
* **Open — Eisermann Theorem 1 on a slice link with `n ≥ 3`** (`research/22`
  §3.4). There `slice` gives only `null V ≥ 1` while `ribbon` demands `n−1 ≥ 2`,
  so unlike the 2-component case the test can fail. It needs a 3-component
  slice link that is not known ribbon; Diao–Pan–Yan's `L(3,2; c/d)` family is
  3-component and is exactly this shape, which is a second reason their
  construction matters.

## 11. Why the sweeps are slow, measured rather than guessed

Profiling the filter on real band output (`K_B`, 485 one-band results at length
2 in 0.5 s): linking numbers and signature are below a millisecond, the
symbolic Fox–Milnor step is 6 ms. **The filter is not the bottleneck.** The
cost is downstream: every link the filter keeps goes through spherogram's
isotopy classification, which builds SnapPy exteriors and runs isometry checks,
seconds apiece. A weaker filter therefore costs time quadratically rather than
linearly, which is the price of dropping Sage's multivariable Fox–Milnor.

A note for whoever tries to win it back: `Link.sublink` silently discards
components that are unknotted *and* unlinked, so the per-component slice test
is real but rarely fires — most one-band offspring have an unknotted component.
The pruning that is actually missing is the multivariable test, and the
one-variable substitute tried here failed calibration (§7).
